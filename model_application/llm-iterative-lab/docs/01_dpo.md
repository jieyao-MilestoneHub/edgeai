# DPO 理論：從偏好選擇到梯度更新

> Direct Preference Optimization
> 本章以指令模型偏好對齊為脈絡，從動機、數學推導到工程流程進行完整解析。

---

## 第 1 章 ｜為什麼指令模型仍不代表「符合偏好」？

假設你已經使用 SFT（Supervised Fine-Tuning）在指令資料集上微調出一個可對話模型，例如：

```
Prompt: 「請解釋區塊鏈是什麼？」
Response: 
區塊鏈是一種去中心化的分散式帳本...
```

模型「看起來會回答問題」，但接下來會出現一系列問題：

| 問題           | SFT 已達成？ | 真實使用者滿意？ |
| ------------ | -------- | -------- |
| 能理解指令        | ✅ 是      | ✅ 是      |
| 語法正確         | ✅ 是      | ✅ 是      |
| 風格自然、人性化     | ⚠️ 部分    | ❌ 有時太制式  |
| 根據情境調整語氣     | ❌ 否      | ❌ 缺乏彈性   |
| 產生更佳回答而非單一答案 | ❌ 否      | ❌ 比較性不足  |
| 能辨識何者是「較優回答」 | ❌ 否      | ❌        |

換句話說：
✅ SFT 能讓模型「會回答」，
❌ 但無法保證「回答方式符合偏好」。

---

### ✅ 偏好是一種「相對性」而非「絕對答案」

例如兩個模型回應：

| Prompt     | 回答 A      | 回答 B       | 人類偏好   |
| ---------- | --------- | ---------- | ------ |
| 「請介紹咖啡因作用」 | 嚴肅冷硬的科學敘述 | 有科學依據但語氣自然 | ✅ B 較佳 |

問題是：SFT 不包含「B 比 A 好」這種訊息，導致模型無法朝偏好方向微調。

---

### 🧠 結論 (第 1 章)

> SFT 掌握了「如何回答」，但沒有學會「什麼是較好回答」。

DPO 的動機正是：讓模型能從「兩個回答誰更好」中學習偏好對齊能力。

---

## 第 2 章 ｜RLHF：早期偏好對齊的標準流程（及其代價）

在 DPO 出現以前，大多數偏好對齊管線都採用 RLHF（Reinforcement Learning from Human Feedback）。其流程如下：

```
(1) SFT：使模型能產生合格回答
(2) 收集偏好對：人類選出較佳回答（chosen vs rejected）
(3) 訓練 Reward Model：輸入 prompt + 回答，輸出偏好分數
(4) 使用 PPO 對 LLM 執行強化學習，使其提升高分回答的機率
```

---

### ✅ RLHF 的優點

| 特性                  | 說明                           |
| ------------------- | ---------------------------- |
| 能以偏好作為訓練訊號          | 不再依賴單一標準答案                   |
| Reward Model 提供相對分數 | 能量化「好 vs 壞」                  |
| PPO 提供策略更新框架        | 模型可被限制不偏離 SFT 太多（KL-control） |

---

### ❌ 但在工程層面存在三大難題

| 問題                      | 說明                                             | 影響      |
| ----------------------- | ---------------------------------------------- | ------- |
| ✅ 難題 1：Reward Model 難訓練 | RM 本身也可能錯誤理解偏好                                 | 決策方向容易歪 |
| ✅ 難題 2：PPO 複雜           | 需處理 advantage estimation、CLIP loss、KL collapse | 訓練極不穩定  |
| ✅ 難題 3：生成回路昂貴           | 每一次更新都需生成、評分、再更新                               | 成本極高    |

---

### 📌 圖解：RLHF 的複雜流程

```
偏好資料 → Reward Model → PPO 策略更新 → 新模型 → 評估 → 迭代
```

此流程具有如下特徵：
✅ 需要額外模型（RM）
✅ 策略更新方式複雜
✅ 每一輪進行「生成→評分→更新」

---

## ✅ 第 2 章結論

| SFT      | 優點       | 缺點 |
| -------- | -------- | -- |
| ✅ 成本低、穩定 | ❌ 缺乏偏好感知 |    |

| RLHF (PPO+RM) | 優點            | 缺點 |
| ------------- | ------------- | -- |
| ✅ 能對齊人類偏好     | ❌ 過於複雜、昂貴、不穩定 |    |

---

好的，以下正式進入 **第 3 章與第 4 章** —— 這兩章是 DPO 的核心：
✅ 第 3 章：從邏輯出發，理解 DPO 是什麼、它「取代了 RLHF 的哪一塊」
✅ 第 4 章：從數學推導出 DPO Loss（公式完整呈現，逐步嚴謹拆解）

---

# 第 3 章 ｜DPO 的核心思維：不做 RL，仍能輸出正確梯度

在第 2 章中，我們看到 RLHF 的成功來自它能根據人類偏好更新模型，但它之所以笨重，是因為它必須經過以下流程：

```
偏好 → Reward Model → PPO → LLM 更新
```

❗問題是：**真的需要 Reward Model 嗎？**
❗真的需要 PPO 進行強化學習嗎？

### ✅ DPO 的關鍵觀察：

> 如果我們已經知道「回答 A 比回答 B 好」，可否直接用這件事更新模型？

這正是 DPO（Direct Preference Optimization）要做到的事。

---

### 📌 DPO 的資料型態（偏好對）

| prompt   | chosen（較好回答） | rejected（較差回答） |
| -------- | ------------ | -------------- |
| "解釋量子糾纏" | ✅ 回答 A       | ❌ 回答 B         |

我們希望模型學會：

```
Pθ(chosen | prompt) > Pθ(rejected | prompt)
```

並透過 loss 來加強這個不等式。

---

### ✅ 與 RLHF 比較流程

| 方法   | 需要 Reward Model | 是否需生成回路 | 是否使用 PPO | 梯度來源        |
| ---- | --------------- | ------- | -------- | ----------- |
| RLHF | ✅ 是             | ✅ 是     | ✅ 是      | Reward 差異   |
| DPO  | ❌ 否             | ❌ 否     | ❌ 否      | log-prob 差異 |

---

### ✅ DPO 的更新邏輯（最直覺說法）

> **若模型生成 chosen 的機率小於 rejected，則上調 chosen、下調 rejected。**
> 若模型已偏向 chosen，則只進行小幅校正，避免破壞語言流暢性。

而這種行為可以被「對數機率差」對應出來，進而形成可微分的 loss（下一章我們將推導它）。

---

✅ 本章結論：

> DPO 不是「模仿最好的回答」，它是「拉大更好 vs 更差的差距」。
> 它跳過 Reward Model 與 PPO，直接優化機率比值，因此稱為「Direct Preference Optimization」。

---

# 第 4 章 ｜DPO Loss 推導：從人類偏好分佈到可優化目標

本章將正式從數學角度推導出 DPO Loss。
這是理解 DPO 的核心，也是面試時能區分你是否真正懂偏好對齊。

---

## ➤ Step 1：從偏好開始

根據偏好資料，我們有以下假設：

```
對於任一 prompt x，
若人類偏好 y⁺ 胜於 y⁻，
則模型應該滿足：
  Pθ(y⁺ | x) > Pθ(y⁻ | x)
```

為了讓這個關係可微分，我們使用對數比率：

```
log(Pθ(y⁺|x)) - log(Pθ(y⁻|x))  越大越好
```

這是一個可直接優化的方向。

---

## ➤ Step 2：加入 KL 正則，避免模型漂移

若只提升 chosen 的概率，模型可能瘋狂改寫語氣、胡亂取巧。
因此 DPO 引入一個 fixed reference model π_ref（通常為 SFT base model），希望其更新方向維持一定距離。

目標變為最大化：

```
[模型對優答案的偏好] - β · [模型與參考模型的 KL 距離]
```

---

## ➤ Step 3：將此目標具體化為 Loss

DPO 論文利用對數優勢轉換（log-odds trick），最終得到：

[
\mathcal{L}(\theta)
===================

* \mathbb{E}*{(x, y^+, y^-)}
  \Big[
  \log \sigma
  (
  \beta[
  \log \pi*\theta(y^+|x)
*

## \log \pi_\theta(y^-|x)

(\log \pi_{\text{ref}}(y^+|x) - \log \pi_{\text{ref}}(y^-|x))
]
)
\Big]
]

其中：

| 符號    | 意義                          |
| ----- | --------------------------- |
| β     | 控制模仿程度 vs 偏好強化的強度           |
| π_ref | 基準模型（通常是 SFT 模型）            |
| σ     | sigmoid，將 log-odds 映射為偏好可信度 |

---

### ✅ 解釋這個 Loss 在做什麼

| 目標      | 行為           |    |                              |
| ------- | ------------ | -- | ---------------------------- |
| 若 πθ(y⁺ | x) ≫ πθ(y⁻   | x) | σ() 趨近 1 → Loss 接近 0 → 更新減弱  |
| 若 πθ(y⁺ | x) ≤ πθ(y⁻   | x) | σ() 趨近 0 → Loss 大 → 促使模型拉開差距 |
| β 大     | 偏好強化更明顯，但易漂移 |    |                              |
| β 小     | 更新較溫和，偏好對齊較慢 |    |                              |

---

✅ 這個 Loss 將偏好對變成「誰應被推高，誰應被拉低」的明確梯度，完全跳過 reward model 與 PPO 的框架。

---

# 第 5 章 ｜β 的角色：在「模仿」與「偏好放大」之間的平衡

DPO loss 中的 β 並不是單純調整梯度大小的常數，它直接決定模型**應該多強烈優先偏好 chosen，還是維持與 reference model 的一致性**。

回顧 Loss：

[
\mathcal{L}(\theta)
===================

* \mathbb{E}*{(x, y^+, y^-)}
  \log \sigma
  (
  \beta[
  \log \pi*\theta(y^+|x)
*

## \log \pi_\theta(y^-|x)

(\log \pi_{\text{ref}}(y^+|x) - \log \pi_{\text{ref}}(y^-|x))
]
)
]

✅ 當 β ↑ 時：

| 行為       | 影響                                |
| -------- | --------------------------------- |
| 偏好對差異被放大 | chosen vs rejected 的 Logit 差距急速拉大 |
| 模型強力偏向偏好 | 更快學會人類喜好                          |
| 但更容易語氣漂移 | 可能變得「刻意討好」「過分安全」                  |

✅ 當 β ↓ 時：

| 行為           | 影響          |
| ------------ | ----------- |
| 偏好差異影響變小     | 偏好調整較溫和     |
| 與 SFT 模型趨於一致 | 保留原始語氣與風格   |
| 但偏好對齊效果較弱    | 需要更多 epochs |

✅ 實務建議：

| 模型規模         | 建議 β              |
| ------------ | ----------------- |
| 小模型（≦3B）     | 0.1～0.2           |
| 中等模型（7B～14B） | 0.1～0.3           |
| 大模型（≥70B）    | 需搭配 KL-Monitor 調整 |

✅ 工程策略（進階）：

> 在迭代訓練中動態調整 β：當 KL 偏離 reference 模型過大時降低 β。

---

# 第 6 章 ｜從訓練流程看 DPO：不是替代 SFT，而是接力 SFT

DPO 並不負責教模型「怎麼回答」，而是「在已有能力的基礎上，傾向人類更喜歡的回答」。
因此正確順序是：

```
(1) SFT：學會遵循指令
(2) DPO：學會在多種表達中選擇較佳方式
```

---

## ✅ 標準工程流程圖

```
┌────────────────────────────────────────┐
│          1. SFT 模型 (π_ref)           │
│  - 輸入：prompt → 回答                 │
│  - 僅學會「怎麼回應」                   │
└────────────────────────────────────────┘
                │
                ▼
┌────────────────────────────────────────┐
│      2. 收集偏好對 (chosen vs rejected)│
│  - 來源：人類評審 / 自動打分器 / A/B   │
└────────────────────────────────────────┘
                │
                ▼
┌────────────────────────────────────────┐
│       3. DPO 訓練 (π_θ vs π_ref)       │
│  - 讓模型逐步傾向 chosen               │
│  - 控制 β，避免ㄧ次性偏離太多         │
└────────────────────────────────────────┘
                │
                ▼
┌────────────────────────────────────────┐
│       4. 部署並持續收集新偏好對        │
│  → 進入下一輪 SFT+DPO 迭代             │
└────────────────────────────────────────┘
```

---

### ✅ SFT 與 DPO 是「接力」而不是「替代」

| 任務       | SFT         | DPO      |
| -------- | ----------- | -------- |
| 學會遵循指令   | ✅           | ❌        |
| 學會選擇較佳回答 | ❌           | ✅        |
| 建立語言能力   | ✅           | ❌        |
| 植入人類偏好   | 少量（取決SFT資料） | ✅        |
| 修正語氣、冗長度 | ❌           | ✅        |
| 替換 RLHF  | ❌（不同任務）     | ✅（更簡化版本） |

✅ 因此完整實務管線通常是：

> **「Base → SFT → DPO → Evaluate → Iterate」**

---

# 第 7 章 ｜DPO vs PPO vs ORPO：三種偏好優化法背後的本質差異

DPO 是 RLHF 的簡化版本，但不是唯一的強化學習替代方案；在偏好優化中，它常與 PPO（RLHF 預設方法）與 ORPO（2024 年提出）並列比較。

---

## ✅ PPO（RLHF 中使用）

| 特徵                 | 說明                            |
| ------------------ | ----------------------------- |
| 搭配 Reward Model 使用 | 必須先訓練 RM                      |
| 需生成 & 評分           | 每步更新前需生成新樣本                   |
| 使用強化學習思想           | 採策略梯度演算法（Policy Optimization） |
| 使用 KL clip         | 控制策略偏移                        |
| 訓練不穩定              | 易 collapse                    |
| 計算成本高              | 需反覆生成                         |

✅ 優勢：功能最全面，可做探索式學習
❌ 工程成本最高

---

## ✅ DPO（Direct Preference Optimization）

| 特徵              | 說明                 |
| --------------- | ------------------ |
| 不需 Reward Model | 直接使用偏好對            |
| 不需生成過程          | 在固定資料集上學習          |
| 無 RL 概念         | 不是策略梯度，而是標準對比式優化   |
| 使用 Log-odds 更新  | 將偏好轉為概率差           |
| 訓練穩定            | 行為接近 cross entropy |

✅ 優勢：簡潔、穩定、成本低
❌ 無法探索未知表達方式，只能在現有回答之間偏好學習

---

## ✅ ORPO（Odds Ratio PPO, 2024）

| 特徵            | 說明                       |
| ------------- | ------------------------ |
| 結合 SFT 與 DPO  | 直接把偏好 loss 嵌入 SFT        |
| 基於 odds ratio | 與 DPO 形式相近               |
| 更接近分類式學習      | chosen vs rejected 作為二分類 |
| 無需 RM、無需 RL   | 行為近似 DPO                 |
| 可單輪訓練完成       | 無需兩階段流程                  |

✅ 優勢：更無縫結合 SFT
❌ 缺少明確 KL 手控，易偏移風格

---

## ✅ 小結表格

| 方法   | 是否需 RM | 是否 RL | 更新時是否生成 | 是否易控制語氣漂移  | 訓練複雜度 |
| ---- | ------ | ----- | ------- | ---------- | ----- |
| PPO  | ✅      | ✅     | ✅       | ⚠️ 須 KL 控制 | 🔴 高  |
| DPO  | ❌      | ❌     | ❌       | ✅ 藉 β 控制   | 🟢 低  |
| ORPO | ❌      | ❌     | ❌       | ⚠️ 無參考模型   | 🟡 中  |

✅ 工程用途結論：

> 如果模型已具備充分能力，只想「讓模型更貼近人類偏好且不破壞原語氣」→ **選 DPO** 是高性價比解法。

# 第 8 章 ｜工程實務中的關鍵問題：資料、漂移與穩定性管理

即使 DPO 很簡潔，實戰仍需注意三個核心問題：

---

## 1️⃣ 資料品質：偏好是否一致、足夠？

DPO 成效高度依賴偏好對（chosen vs rejected）的品質，問題包括：

| 問題類型                   | 影響         |
| ---------------------- | ---------- |
| chosen 與 rejected 差異太小 | 梯度改變薄弱     |
| 偏好理由不一致                | 學不到穩定語氣    |
| 人工標註偏誤                 | 導致模型偏激     |
| 自動打分器不可靠               | 無法真正反映人類偏好 |

✅ 改善策略：
✔ 使用「風格差異明顯」偏好對
✔ 使用軟偏好分數進行篩選
✔ 每輪抽樣人工審核

---

## 2️⃣ 漂移管理：如何避免回答變得「過度迎合」或「無限冗長」？

當 β 過大或偏好對不平衡時，模型可能出現：

| 現象     | 例                   |
| ------ | ------------------- |
| 語氣過度諂媚 | 「親愛的使用者，您的請求真是太棒了！」 |
| 回答冗長   | 強迫加入解釋與保險語句         |
| 過度安全   | 凡是可能敏感的題目全拒答        |

✅ 解法：
✔ 僅在高品質偏好對上執行 DPO
✔ 監測與 reference model 的 KL divergence
✔ 加入「簡潔勝過冗長」的偏好對

---

## 3️⃣ 訓練穩定性：何時中止、何時觸發下一輪迭代？

常見策略：

| 判斷指標     | 建議                 |
| -------- | ------------------ |
| 開始 DPO   | 偏好對 ≥ 1k           |
| 結束 DPO   | validation loss 收斂 |
| 是否回到 SFT | 若語氣漂移過大            |
| 是否繼續     | 若 win-rate 仍提升     |

---

✅ 小結（工程最佳實務）：

> 「先用 SFT 建立能回應的模型，再使用高品質偏好對進行 DPO，並透過 β 與 KL 控制更新幅度，確保模型不漂移。」

# 第 10 章｜從理論到落地：DPO 在實戰中的完整管線設計

DPO 並不是獨立替代方案，而是一個「在 SFT 基礎上進行偏好對齊的中段模塊」。因此，實戰流程必須依據組織規模、資料量與產品成熟度來動態調整。

---

## ✅ 標準流程：SFT + DPO 的閉環優化管線

```
   ┌──────────────────┐
   │  1. SFT 模型     │  ← 建立「可用」指令模型
   └────────┬─────────┘
            │
            ▼
   ┌──────────────────┐
   │  2. 收集偏好對     │  ← chosen vs rejected
   └────────┬─────────┘
            │
            ▼
   ┌──────────────────┐
   │  3. 執行 DPO 對齊  │  ← 放大偏好差異，設定 β
   └────────┬─────────┘
            │
            ▼
   ┌──────────────────┐
   │  4. 評估 + 監控    │  ← Win-rate、KL 漂移
   └────────┬─────────┘
            │
            ▼
   ┌──────────────────┐
   │  5. 是否進下一輪？│───► 若偏好不夠好 → 回到 (2)
   └──────────────────┘
```

---

## ✅ 啟動條件：什麼時候開始 DPO？

| 條件                       | 是否啟動 DPO |
| ------------------------ | -------- |
| SFT 模型尚不穩定，答題經常錯誤        | ❌ 不開始    |
| 偏好對少於最低門檻（例如 300～1000 對） | ❌ 不開始    |
| chosen 與 rejected 差異不明顯  | ❌ 不開始    |
| 模型回答已可用，但缺乏一致風格或偏好表現     | ✅ 啟動 DPO |

---

## ✅ 小型 / 個人實驗者流程（模型 ≤3B / 無線上流量）

| 階段   | 作法                       | 備註                      |
| ---- | ------------------------ | ----------------------- |
| SFT  | 使用公開 instruction dataset | e.g. Alpaca, OpenHermes |
| 偏好收集 | 自行生成並手動選優                | 人力小但精準                  |
| DPO  | 小 batch + β=0.1~0.2      | 避免漂移過大                  |
| 評估   | 自行對照前後作答                 | 人工質檢                    |
| 迭代   | 3～5 輪，直至語感穩定             | 縮小資料集迭代                 |

✅ 適合：研究生、個人開發者、小型創業實驗

---

## ✅ 團隊實作流程（3B~14B / 有初步用戶回饋）

| 階段   | 作法                                | 管控重點          |
| ---- | --------------------------------- | ------------- |
| SFT  | 多輪指令增強                            | 建立多場景泛化能力     |
| 偏好收集 | 人工標註 + 規則 + LLM 評估助理              | 提升數量與一致性      |
| DPO  | 低步數試行 + KL 漂移監測                   | 防止語氣失控        |
| 評估   | 使用 win-rate + BLEU + success rate | 結合自動與人工       |
| 迭代   | 每週/雙週循環                           | 有定期 gate pass |

✅ 適合：新創團隊 / Infra 模型組

---

## ✅ 企業級閉環流程（>7B / 線上流量足夠）

| 元素           | 設計內容                             |
| ------------ | -------------------------------- |
| 資料引擎         | 從線上回饋自動挖掘被 downvote / upvote 回應  |
| 偏好對生成        | 使用 Tempered sampling + reranking |
| 人審驗證         | 選擇 top-K & bottom-K 做人工精審        |
| DPO Schedule | 滾動式（每週/每日）                       |
| 漂移監控         | 動態 β 調整 & 參考 KL 遠離閾值             |
| 安全守門         | 加入拒答偏好對 (拒優迎劣控制)                 |
| 發版節奏         | Canary rollout + AB test         |

✅ 模型生命週期形成真正「增強學習系統（但非 RL HF）」
